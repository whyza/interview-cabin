# 开发工作流程

## 工作模式

### 记忆唤醒
查 CLAUDE.md + rules + 项目记忆 → 严禁跳过

### 分析规划
Grep/Glob/Read 理解代码 → 复杂任务先出方案 → 禁止凭空臆测

### 编写行动清单
分解任务 → 列清单待批准 → 未经批准不得执行

### 执行开发
Read/Edit/Write 精确操作 → 并行修改独立文件 → 改完编译验证

### 质量检查
对照 coding-style 自查 → **等用户指令决定是否 review** → 不主动送审

### 快速响应
简单请求直接处理

## 核心原则

- **精确性优先**：不确定立即查证，禁止臆测
- **简洁沟通**：涉及代码附带文件路径和行号
- **不主动扩展**：用户让做 A 就只做 A，发现 B 有问题只提示
- **改动即编译**：每次改完跑 `mvn -q compile -pl <模块> -am -o -DskipTests` 确认通过
- **每次交互结尾必须调用 AskUserQuestion 确认**

## 大任务完成后记本地 memory

**触发时机**：完成一个较大的任务后（新增/改造 3+ 文件、跨模块改动、功能点从零到可用、
排查并修复了非显而易见的缺陷）。零散的小修改不记。

**写在哪**：工程目录下的 `docs/memory/YYYY-MM-DD.md`（`docs/` 已 gitignore，不进仓库）。

**格式**：一天一个文件，追加当天的任务段落：

```markdown
# 2026-09-23

## 箱唛需求推送 · 前置校验与自动推送挂起

### 背景
SCM 推送接口未就绪，先做与推送通道无关的部分。

### 改动内容
- `IRequirementPushService` / `RequirementPushServiceImpl`：前置校验、确认无需推送、自动推送判定
- `RequirementPushRecordFactory`：挂起记录组装
- `RequirementWriteBackHandler`：三个分支各补一次自动推送判定

### 关键坑（重要）
包装数据不需要校验——需求新增与箱唛任务建单两条路径都有必填校验，
在推送前置校验里重复判断是多余的。用户指正后已删除。

### 决策与取舍
- 挂起记录不写文件快照（此时没文件），不参与失败重试扫描（等的是补传事件不是时间）
- `hasPendingRecord` 防重复：judgeAutoPush 会被重复回调触发，不判重会堆出多条相同记录

### 未完成 / 待办
- 推送动作本身待 SCM 接口就绪后接入
- 补传文件后的自动推送触发链路未做
```

**要记什么**（按价值排序）：

1. **关键坑** —— 踩过的雷、被指正的地方、非显而易见的约束。这是最有价值的部分
2. **决策与取舍** —— 为什么这么做，放弃了什么方案
3. **未完成 / 待办** —— 下次接着做的线索
4. 改动内容 —— 简述即可，代码本身就是记录

**不要记**：常规的 CRUD 实现细节、能从代码直接看出来的东西、流水账式的操作过程。
