# Agent 编排 & 规范

## 核心原则

除 **review 类 Agent** 外，其他 Agent 由我按需自行决定是否调用。

**review 类（`code-reviewer`）必须等用户明确要求**，不主动送审。

## 代码审查怎么做

**默认自己审**，不叫 agent。自己审的成本是几秒，叫 agent 是十几到几十分钟——
因为子 agent 是全新上下文，必须从零读文件、grep 调用方重新建立理解，
我们这边已有的认知它要重走一遍。

自查方式：看 `git diff`（不是整个文件），对照 coding-style 清单过一遍。

**用户要求审查时**，必须做到：

1. 给 **diff** 而不是整个文件（`git diff HEAD~1 -- <路径>`）
2. 把关键上下文**写进 prompt**（改了什么、为什么、已知取舍），别让它自己推导
3. **限定范围**：指定方法/类，不要写"审全链路"
4. **加止损**："找到 N 个问题就停"、"只审 X 方法"
5. 一次不超过 3-5 个文件

反例（耗时 27 分钟、108 次工具调用）：给 14 个文件 + 每个文件 4-6 个开放子问题。

## 调用规则

| 场景 | Agent | 触发条件 |
|------|-------|---------|
| 代码审查 | code-reviewer | **用户明确要求**（"review"、"审查"、"检查一下"、"过一遍"） |
| 安全审查 | security-reviewer | **用户明确要求** |
| 方案规划 | planner | 改动跨 3+ 模块、架构调整、需求有歧义时，自行判断调用 |
| 构建失败 | build-error-resolver | `mvn compile/test` 失败且自查无果，自行判断调用 |
| 代码库探索 | Explore | 大规模搜索、理解跨模块关系，自行判断调用 |
| 文档更新 | doc-updater | 需要更新文档时自行判断调用 |

### 禁止行为

- **禁止写完代码自动送 review**。审查由用户决定时机，不是流程的默认收尾动作
- **禁止自行扩大范围**：用户让改 A，不要顺手改 B、C，有问题只提示不动手
- **禁止重复造轮子**：写工具方法/常量前先搜仓库，已有类似实现直接用（枚举里可能已有现成判定方法）
- 禁止主观臆测技术细节，禁止编造不存在的 API、不存在的字段

### 测试

仅在用户明确要求时编写和运行测试。命令参考：

```
mvn test                           # 全部测试
mvn test -Dtest=类名               # 单个测试类
mvn test -pl ai-service -am        # 指定模块
mvn clean install -DskipTests      # 跳过测试
```

### 知识获取

1. **Grep/Glob** 搜索项目代码 — 项目内有类似实现时优先参考
2. **Agent(Explore)** 探索代码库 — 大规模搜索或理解模块关系
3. **WebSearch** 查官方文档 — 项目代码找不到参考时
